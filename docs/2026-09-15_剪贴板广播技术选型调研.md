## 1. 场景拆解

| # | 场景 | 数据流 | 关键约束 |
|---|------|--------|----------|
| 1 | 小米手机复制验证码 → PC 收到 | Android → LAN 广播 → Windows | Android **后台**读剪贴板受限（核心难点） |
| 2 | PC 复制 URL → 小米平板收到 | Windows → LAN 广播 → Android | 接收端写入剪贴板 + 通知；自动拉起浏览器放 v1.x 增强 |
| 3 | 电脑复制淘口令 → 手机淘宝自动识别 | PC → LAN → 手机剪贴板 → 淘宝读取 | 只需把内容**写入手机剪贴板**，跳转由淘宝自己完成 |

共同模型：

```
复制事件(源端) → 采集 → 去重/防回环 → 加密 → LAN 组播/直连 → 配对设备解密 → 写入剪贴板 + 通知
```

## 2. Android 采集方案：无障碍服务（已锁定）

### 2.1 原理

Android 10+ 禁止后台 App 读剪贴板（`getPrimaryClip()` 返回空），但有两条可组合的路径：

1. **无障碍服务感知复制事件**：AccessibilityService 监听系统事件流（文本选择菜单点击、`TYPE_VIEW_TEXT_CHANGED`、复制弹窗「已复制」Toast/控件），判断「用户刚执行了复制」；
2. **透明 Activity 瞬时获焦读剪贴板**：检测到复制事件后，从无障碍服务拉起一个 0 像素/透明的 Activity（前台窗口即获得读剪贴板资格），读取后立即 `finish()`。用户无感知。

> 无障碍服务在后台拉起 Activity 属于系统允许的豁免场景（Android 10~14 的 BAL 限制均豁免 AccessibilityService），这是 FV 悬浮球等工具验证过的成熟模式。

### 2.2 备用兜底（自用场景完全可接受）

由于是自用工具，可以再备两条路：

- **AppOps 一次性授权**（最省事）：`adb shell appops set <pkg> READ_CLIPBOARD allow`，之后后台直读剪贴板，无障碍只做事件感知。换机/重装需重新执行。
- **前台服务 + 悬浮球手动广播**：自动化失效时的手动兜底。

### 2.3 接收端（场景 2、3 的落点）

- 后台**写**剪贴板：多数 ROM（含 MIUI/HyperOS）允许，无障碍+前台服务常驻进一步降低被杀概率；
- 收到内容后：写入剪贴板 → 发一条本地通知（「已收到来自 PC 的 URL，点击打开」）；
- 保活三件套：前台服务 + 引导用户开「自启动 / 无限制省电 / 锁后台」，提供一键跳转系统设置页。

### 2.4 平台能力小结

```
Windows：监听✅ 写入✅ 后台✅            —— 无难点（AddClipboardFormatListener）
Android：采集✅(无障碍+透明Activity) 写入✅ 保活⚠️ —— 无障碍方案已覆盖
```

## 3. 传输层：纯 LAN + 设备配对（已锁定）

### 3.1 为什么砍掉 BLE 和公网

- BLE：带宽 10-50KB/s、双端开发体验差、断连管理复杂，纯文字场景 WiFi 已全覆盖 → 砍掉；
- 公网中继：自用离线工具无跨网段需求，砍掉后顺带消灭服务器成本、账号体系、隐私信任三座大山。

### 3.2 防串扰设计：配对（Pairing）先行

同一局域网可能有其他人（家人/同事）也装了这个工具，必须保证「只有我的设备之间能互通」。设计如下：

**发现层（公开，无敏感信息）**
- 各端通过 mDNS 广播服务 `_clipbordcast._tcp.local`，TXT 记录携带：设备 ID（随机 UUID）、设备名（「Sothe-PC」「小米14」）、协议版本、TCP 端口；
- 发现 ≠ 信任。未配对设备在列表里显示为「待配对」。

**配对层（一次性，TOFU）**
```
设备A(发起)                    设备B(确认)
   │── TCP 连接 + 握手请求 ──────▶│
   │                              │ 弹出 6 位配对码 (SAS)
   │◀──── 用户把B上的码输入A ──────│
   │── 以配对码为口令完成 PAKE ───▶│   (SPAKE2，防中间人)
   │◀── 交换设备长期公钥(Ed25519)─▶│   双方各自落盘 pinned
   │       配对完成，双向信任       │
```

- 6 位码 60 秒过期、仅展示一次；连续失败 3 次锁定 5 分钟；
- 配对成功后双方持久化对方公钥（TOFU，类似 SSH/KDE Connect）；
- 支持「取消配对」：本地删除对方公钥即永久断交。

**通信层（仅配对设备可达）**
- 传输：TCP 直连，**TLS 1.3**，各端用配对时交换的 Ed25519 公钥派生的自签证书，双向校验 + 证书锁定（pinning）；
- 未配对设备的连接直接拒绝 → **串扰在握手层就被掐死**，同网段其他人即使发现服务也收不到任何内容；
- 消息加密之外再无应用层明文，LAN 抓包只能看到 TLS 密文。

### 3.3 广播语义与防回环

消息格式（JSON over TLS）：

```json
{
  "v": 1,
  "msgId": "uuid-v4",
  "from": "device-uuid",
  "ts": 1758030759123,
  "type": "CLIP_TEXT",
  "payload": { "text": "839201" },
  "hash": "sha256(text)"
}
```

- **广播**：一端复制 → 向所有已配对且在线的设备逐条 TLS 直连发送；
- **去重**：各端维护最近 5 秒内的 `(hash, ts)` 窗口，收到与本地刚写入相同 hash 的消息直接丢弃 → 防回环（A 写剪贴板 → 广播 B → B 写入触发监听 → 不广播回来）；
- **TTL**：消息 60 秒有效，过期丢弃；接收端可选「60 秒后自动清空剪贴板」；
- **大小**：纯文字上限 64KB（足够长文 + 富文本场景，超限截断并提示）。

## 4. 客户端技术栈（已锁定）

### 4.1 Android 端 — Kotlin 原生

| 模块 | 选型 |
|------|------|
| 语言/UI | Kotlin + Jetpack Compose（设置页、配对页、通知） |
| 剪贴板采集 | AccessibilityService + 透明 Activity（§2.1） |
| 常驻 | ForegroundService（`foregroundServiceType="dataSync"`） |
| 发现/网络 | Android NSD（mDNS）+ OkHttp/Netty 或裸 Socket + Conscrypt TLS |
| 加密 | Bouncy Castle / Tink（Ed25519 + SPAKE2 + TLS1.3 pinning） |

### 4.2 Windows 端 — Tauri 2（内存/CPU 敏感）

| 模块 | 选型 |
|------|------|
| 壳 | Tauri 2（系统 WebView2，安装包 <10MB，常驻内存预期 20~40MB，比 Electron 低一个数量级） |
| 核心逻辑 | **Rust 侧全包**：剪贴板监听、网络、加密、配对，WebView 只做设置界面 |
| 剪贴板监听 | Win32 `AddClipboardFormatListener`（可用 `windows` crate 直调，或 `clipboard-win`） |
| 剪贴板写入 | `arboard` crate |
| mDNS | `mdns-sd` crate（纯 Rust，无依赖地狱） |
| TLS/加密 | `rustls` + `ring` / `ed25519-dalek` + `spake2` |
| 常驻形态 | 托盘程序（`tauri-plugin-tray`），开机自启（`tauri-plugin-autostart`） |
| CPU 占用 | 事件驱动，空闲时 ≈ 0%（无轮询） |

> 明确排除 Electron：常驻 200MB+ 内存与一个「离线小工具」的定位不符。
> 排除 Flutter 桌面：包体与内存仍偏重，且原生桥接工作量没有省掉。

### 4.3 双端协议共享

协议层（消息格式、配对握手流程、去重规则）写成一份**协议文档** `docs/protocol-v1.md` 作为双端唯一事实来源；不追求共享代码（Rust↔Kotlin 跨语言绑定成本 > 收益，自用项目文档同步足够）。

## 5. 安全设计（纯 LAN 版）

| 项 | 设计 |
|----|------|
| 信任建立 | 6 位 SAS 码 + SPAKE2 配对，TOFU 锁定对方公钥 |
| 传输加密 | TLS 1.3 + 双向证书校验 + pinning，LAN 抓包只见密文 |
| 防串扰 | 未配对设备握手即拒（§3.2） |
| 敏感内容 | 可选规则：匹配正则（如 6 位数字验证码）的消息 60 秒后自动从剪贴板清除 |
| 密码管理器 | Windows 端识别 `Clipboard Viewer Ignore` 标记，不广播 1Password 等写入的内容 |
| 本地存储 | 配对密钥 Android 存 Keystore / Windows 存 DPAPI 保护目录 |
| 攻击面 | 不监听公网、无云端、无账号 → 攻击面收敛到「同网段且能诱导用户输入配对码」 |

## 8. 附：v1 调研时否决的方案备查

| 方案 | 否决原因 |
|------|----------|
| BLE 传输 | 带宽小、开发重，纯文字被 WiFi 全覆盖 |
| 公网中继/MQTT | 自用离线工具无跨网段需求 |
| Electron | 常驻内存 200MB+，与定位冲突 |
| Flutter 全平台 | 桌面端偏重，原生桥接成本没省 |
| iOS 端 | 系统层面不可行（后台无法监听剪贴板） |
| 短信/通知栏监听采集 | 只覆盖验证码，不满足「任意文字复制」 |
